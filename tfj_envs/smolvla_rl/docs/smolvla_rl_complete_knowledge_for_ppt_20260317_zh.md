# SmolVLA + Flow Matching + Hybrid RL 全量知识总纲

这份文档的目标不是复现实验，而是把对话中已经涉及到的知识点、思考框架、概念解释、系统拆解、训练逻辑、上机逻辑和常见误区，整理成一份适合下游 AI 继续加工成 PPT 的统一素材。

因此本文档有三个原则：

1. 尽量去项目化，不依赖具体路径和一次性实验上下文。
2. 尽量覆盖全知识面，而不是只讲代码实现。
3. 尽量把“概念层”“系统层”“训练层”“上机层”“工程坑点”分开说清楚。

## 1. 一句话总览

这套工作的核心主题可以概括成一句话：

- 用一个多模态 VLA 模型作为行为策略主体，用 flow matching 作为连续动作 chunk 的生成方式，再在离线行为克隆基座之上叠加 hybrid RL 微调，最后把训练后的 actor 部署到真实机器人上执行和评估。

如果再拆细一点，整个主题包含五个层面：

1. 模型层：
   - 什么是 SmolVLA，它内部怎么把图像、语言、状态组织成动作输出。
2. 动作建模层：
   - 什么是 flow matching，它和直接回归、ACT 这类方法有什么差别。
3. 强化学习层：
   - 怎么把 reward、value、advantage、replay buffer、collector 接到 SmolVLA 上。
4. 训练流程层：
   - 为什么通常要先离线训练，再做 RL 微调，而不是从零直接 RL。
5. 部署层：
   - 训练好的模型怎么上机，推理时“用了 RL”到底是什么意思。

## 2. 先把几个容易混淆的概念拆开

做这类项目时，最容易把下面几件事混成一件事：

1. 动作生成器：
   - 模型最后到底是“直接回归动作”，还是“生成动作 chunk”，还是“用 flow matching 逐步去噪得到动作”。
2. 训练目标：
   - 训练时到底是纯监督学习、纯 RL，还是监督学习和 RL 的混合。
3. 运行时行为：
   - 机器人执行时，到底是在“只推理”，还是“边执行边更新参数”。

这三件事必须分开看。

一个系统完全可能是：

- 推理时用 flow matching 生成动作；
- 训练时同时使用离线监督损失和在线 RL 损失；
- 上机执行时只做 actor 推理，不做任何在线更新。

所以讨论“有没有 RL”“是不是 flow matching”“是不是上机”时，必须先问清楚你说的是：

- 模型结构
- 训练损失
- 运行方式

## 3. VLA 是什么，SmolVLA 是什么

### 3.1 VLA 的一般定义

VLA 可以理解成“Vision-Language-Action”模型，即：

- 输入里有视觉信息
- 可能有语言任务描述
- 也通常有机器人状态
- 输出是机器人动作

它和只看图像做分类的视觉模型不同，也和只生成文本的语言模型不同。

它更接近一种“多模态条件控制器”。

### 3.2 SmolVLA 的一般结构直觉

SmolVLA 的核心直觉是：

1. 先把图像、语言、状态编码成统一的前缀表征。
2. 再在这个前缀表征之上生成未来一段动作 chunk。

所以它不是“一次只出一个动作”的最简单控制器，而更像：

- 先理解当前观测和任务
- 再一次性规划一小段动作轨迹

这种做法在机器人里有两个直接好处：

1. 降低每步都重新规划的抖动。
2. 更容易利用时序一致性，提升动作平滑性。

### 3.3 SmolVLA 中最重要的几个模块

从系统角度理解，SmolVLA 至少包含这些逻辑模块：

1. 视觉编码模块：
   - 负责把相机图像变成视觉 token 或隐藏特征。
2. 语言编码模块：
   - 负责把任务文本或语言提示转成语言 token 表征。
3. 状态投影模块：
   - 负责把机器人低维状态投影到与主干模型兼容的隐藏空间。
4. 前缀融合模块：
   - 负责把图像、语言、状态组织成统一的 prefix context。
5. 动作生成模块：
   - 负责在 prefix context 条件下生成未来动作 chunk。
6. 价值估计模块：
   - 在引入 RL 后，用同一个 prefix context 估计 value。

这意味着 SmolVLA 的结构重点不是“某一个特别复杂的头”，而是：

- 多模态统一编码
- chunk 级动作生成
- 同一份共享表征同时服务 actor 和 critic

## 4. shared prefix representation 到底是什么

这是整个系统里非常重要的概念。

### 4.1 直觉解释

所谓 shared prefix representation，可以理解成：

- 模型先把“当前这一刻对任务真正有用的信息”压缩成一份统一上下文

这份上下文来自：

- 当前图像
- 当前语言任务
- 当前机器人状态

然后：

- actor 用它来生成动作
- value head 用它来估计未来回报

也就是说，actor 和 critic 不是各自重新做一遍完整的编码，而是共享同一份“前缀语义表征”。

### 4.2 为什么它重要

它重要有三个原因。

第一，计算复用。

- 同一份多模态编码结果可以同时给动作头和值函数用。
- 这样比 actor 编一遍、critic 再编一遍更省算力。

第二，语义对齐。

- actor 和 critic 看到的是同一种状态语义抽象。
- 这样 critic 学到的“这个状态好不好”更容易和 actor 的行为逻辑对齐。

第三，更适合在大 backbone 上做增量改造。

- 当你不想重写整个 VLA，只想把 RL 接进去时，最自然的做法就是复用 prefix 表征，在其上额外接 value head。

### 4.3 它也不是没有代价

共享表征也有代价。

1. actor 和 critic 会相互牵制。
2. 如果 prefix 本身偏差很大，那么动作和值估计都会一起受影响。
3. 如果 critic 的目标变化很快，可能会反向影响 actor 所依赖的共享表示。

所以在工程实现里，常常需要通过：

- 权重控制
- 冻结部分 backbone
- 限制 RL 分支强度

来避免共享表征被 RL 训练拉得过猛。

## 5. 动作建模：直接回归、ACT、flow matching 分别是什么

### 5.1 直接回归动作

最简单的方法是：

- 给定观测，直接预测动作向量

优点：

- 简单
- 推理快
- 容易实现

缺点：

- 多峰动作分布难建模
- 连续轨迹平滑性通常不够好
- 对复杂时序模式不够灵活

### 5.2 ACT 的基本思路

ACT 的核心关键词是 action chunking。

它不强调一次只预测一个动作，而是：

- 一次预测未来一小段动作序列

其典型优势是：

- 利用 chunk 结构提升时序一致性
- 推理时更平滑
- 比单步直接回归更适合机器人轨迹控制

如果只看“大类”，ACT 和 SmolVLA 并不是完全对立的。

它们都重视：

- chunk 级动作预测
- 条件控制
- 用统一上下文预测短时未来动作

### 5.3 flow matching 的基本思路

flow matching 可以先用非常直觉的话来理解：

- 不直接预测动作本身
- 而是学习“如何把噪声逐步变成动作”的向量场

训练时，常见做法是：

1. 先拿真实动作
2. 加入噪声
3. 随机采样一个时间变量 `t`
4. 让模型学习从当前 noisy action 朝目标动作方向该怎么走

于是模型学到的不是一个点，而是一种连续的“去噪方向”。

### 5.4 flow matching 为什么适合连续机器人动作

机器人动作通常是连续的。

flow matching 在这类问题上的优势包括：

1. 对连续多峰分布更自然。
2. 更容易表达“动作是从粗到细逐步成形”的过程。
3. 生成出来的 chunk 往往比直接回归更平滑。

### 5.5 flow matching 和 ACT 的一般差别

一个简单说法是：

- ACT 更偏“条件下直接输出动作 chunk”
- flow matching 更偏“条件下学习一条从噪声到动作 chunk 的生成动力学”

所以两者的区别不在于是不是都预测 chunk，而在于：

- 一个更像直接条件预测
- 一个更像连续生成过程

### 5.6 为什么不要用参数量直接判断谁更强

“VLA 的参数量是不是比 ACT 小”这类问题，经常会把几个不同指标混在一起。

至少要区分：

1. 总参数量
2. 可训练参数量
3. 推理时真正激活的参数量

在带有大视觉语言 backbone 的系统里，经常会出现：

- 总参数量看起来很大
- 但真正可训练部分只是一小截

因此：

- VLA 不一定比 ACT 更大
- ACT 也不一定比 VLA 更轻
- 参数规模不能直接代表控制能力

真正要看的通常是：

- 模态输入复杂度
- backbone 是否冻结
- 动作头设计
- 训练目标
- 部署约束

## 6. 为什么很多人会先想到“把 flow matching 融进去”

因为从模型结构视角看，最显眼的切入点就是动作头。

如果一个现有 VLA 末尾是某种动作预测模块，那么自然会想到：

- 是否可以把最后的动作生成器替换成 flow matching

这是合理的结构性思路。

但在工程上，必须先澄清：

1. 你要替换的是动作生成方式，还是训练目标。
2. 你要接的是生成模型方法，还是 RL。
3. 你要改的是 actor 本体，还是 actor 外部的训练闭环。

这是对话中一个很关键的经验教训：

- “把 flow matching 接进去”和“把 RL 接进去”不是同一件事。

前者更偏模型结构改造。

后者更偏训练框架扩展。

两者可以同时发生，但必须明确边界。

## 7. 把 RL 融入 SmolVLA，最合理的视角是什么

### 7.1 不是重写一个新模型，而是扩展现有 actor

更工程化的做法通常不是：

- 另起一个完全独立的 RL 网络

而是：

1. 保留 SmolVLA 作为 actor 主体
2. 复用其多模态 prefix context
3. 加上 value head
4. 在训练环节引入 online data、reward 和 value regression

这样做的优点是：

1. 保留原本的离线行为先验
2. 保留成熟的多模态动作生成能力
3. 改动面相对更小
4. 更适合从现有 checkpoint 起步

### 7.2 从工程使用角度，最佳流程通常是分阶段

虽然 hybrid RL 的单步训练里会同时计算多种损失，但从项目推进角度看，通常还是应该分阶段：

1. 先得到一个能工作的离线基座
2. 再做 hybrid RL 微调
3. 再做真实机器人上机验证

这不是语法要求，而是工程稳定性要求。

原因很简单：

- 如果 actor 初始行为非常差，online rollout 的数据质量会很差
- value 学习会更噪
- RL 很容易变成“在坏策略附近做无效更新”

所以“分阶段”说的是项目流程，不是说 hybrid trainer 内部只会先 offline、后 RL。

### 7.3 从单个训练 step 来看，确实是“同时训练”

一个 hybrid step 里通常会发生：

1. 收 online rollout
2. 取 offline batch
3. 取 replay buffer 里的 online batch
4. 算 offline loss
5. 算 online actor loss
6. 算 value loss
7. 三者加权求和
8. 一次反传更新

因此要准确表述的话，应该说：

- 项目流程是先离线、再 hybrid RL
- 但 hybrid trainer 的每个 step 内部是同步混合优化

## 8. 强化学习小白必须先懂的基本概念

### 8.1 什么是 reward、return、value、advantage

reward：

- 环境在一步转移后给的即时反馈

return：

- 从当前时刻开始，未来所有 reward 的折扣和

value：

- 在当前状态下，未来预期 return 的估计

advantage：

- “这次结果比我原本预期好多少或差多少”

它最常见的直觉写法是：

- `advantage = target_value - current_value`

### 8.2 V(s) 和 Q(s, a) 的区别

V(s)：

- 只问“这个状态整体有多好”

Q(s, a)：

- 问“在这个状态下，如果我执行这个动作，会有多好”

可以这么记：

- V 是“状态值”
- Q 是“状态-动作值”

当动作空间很大、而且是连续的时，直接建 Q(s, a) 往往更难。

因此很多工程实现会更偏向：

- actor 负责出动作
- critic 只估 V(s)

### 8.3 随机策略和确定性策略

随机策略：

- 同一个状态下，输出的是动作分布
- 每次可以采样出不同动作

确定性策略：

- 同一个状态下，输出一个固定动作

机器人控制里两者都常见。

随机策略更适合探索。

确定性策略更适合稳定控制。

### 8.4 离散动作和连续动作

离散动作：

- 动作是有限选项，例如“左”“右”“抓”“放”

连续动作：

- 动作是实数向量，例如机械臂 6 维关节控制量

机器人领域大多数低层控制问题都更接近连续动作。

这也是为什么：

- flow matching
- DDPG
- SAC

这类方法在机器人里会很常见。

### 8.5 on-policy 和 off-policy

on-policy：

- 用当前策略刚刚采到的数据训练当前策略

特点：

- 更“新鲜”
- 但样本利用率低

off-policy：

- 可以反复利用过去采集的数据
- 往往借助 replay buffer

特点：

- 样本利用率高
- 更适合昂贵的数据场景

机器人里由于采数据成本高，off-policy 思路很有吸引力。

### 8.6 PPO、DDPG、SAC 分别是什么

PPO：

- 近端策略优化
- 典型 on-policy 方法
- 稳定、常用、容易作为基线
- 但样本利用率不高

DDPG：

- 深度确定性策略梯度
- 典型 off-policy 方法
- 面向连续动作
- actor 通常是确定性策略

SAC：

- 软演员评论家
- 典型 off-policy 方法
- 面向连续动作
- actor 通常是随机策略
- 在探索和稳定性之间通常有不错的平衡

如果给小白一个非常粗略的记忆法：

- PPO：稳定的 on-policy baseline
- DDPG：连续动作、确定性、off-policy
- SAC：连续动作、随机策略、off-policy、工程上常见

## 9. 这套 hybrid RL 更像什么，不像什么

这套实现不是典型的 PPO。

因为它不是靠：

- 当前策略采样
- 再用 PPO clip objective 直接更新策略分布

它也不是标准 SAC/DDPG 的直接翻版。

因为它没有走“传统 actor-critic + Q 函数 + policy gradient”那条完全经典的路线。

它更像一种：

- 离线行为克隆 actor
- 加上共享 prefix 上的 value head
- 用 online rollout 产生 chunk reward
- 再用 advantage-weighted flow matching 继续微调 actor

所以它的核心思想更接近：

- “保守的、以生成式 actor 为主体的 hybrid RL 微调”

而不是：

- “纯策略梯度派”

## 10. reward 函数和 loss 函数不是同一层东西

这是另一个常见误区。

reward 函数：

- 由环境定义
- 决定环境告诉你什么叫好、什么叫坏

loss 函数：

- 由训练器定义
- 决定你如何把 reward 信号转成可微优化目标

可以这样理解：

- reward 解决“学什么”
- loss 解决“怎么学”

在实际系统里，经常会出现：

1. reward 来自环境
2. value target 由 reward 和 bootstrap 组成
3. actor loss 再用 advantage 对生成损失加权

所以 reward、value、actor loss 是一条链，不是一个东西。

## 11. 这类系统里的 reward 通常怎么设计

如果是机器人连续控制，工程上常见的 reward 设计思路是：

1. 密集 shaping 项：
   - 例如距离目标越近 reward 越高
2. 稀疏成功项：
   - 真正完成任务时给额外 bonus

这类设计的优点是：

1. 训练早期也能有梯度方向
2. 不至于只靠稀疏成功信号

缺点是：

1. 可能学到“讨好 shaping”的策略，而不是真正完成任务
2. 仿真里的 shaping 未必对应真实机器人目标

所以 reward 的本质问题不是“能不能写出来”，而是：

- 它是否真的表达了你想要的行为

## 12. chunk 级 rollout 和 chunk 级 reward 聚合

在 action chunk 模型里，训练单位往往不是单一步动作，而是一小段动作序列。

因此 online data 的采样过程通常也是 chunk 级别的。

collector 的一般流程可以概括成：

1. 用当前观测构造 policy 输入
2. 让 actor 预测一个 action chunk
3. 把 chunk 中的动作逐步执行到环境里
4. 在执行过程中累积 reward
5. 形成一个 chunk transition

这个 transition 里通常包含：

1. 当前观测
2. 整个动作 chunk
3. 这个 chunk 对应的折扣累计 reward
4. 下一时刻观测
5. done 标记
6. bootstrap discount

这和传统单步 `(s, a, r, s')` 经验回放很像，但单位从“单步”升级成了“chunk”。

## 13. replay buffer 在这套系统里起什么作用

replay buffer 的作用是：

- 存储 online 收集到的 chunk transition
- 支持随机采样
- 提高数据利用率

这使整个训练具备更强的 off-policy 特征。

在 chunk 场景里，replay buffer 的价值尤其明显，因为：

1. 生成一段动作 chunk 的 rollout 成本不低
2. 每次都只用一次 online 样本太浪费
3. 随机采样有助于打散相关性

## 14. value head 为什么要接在 SmolVLA 上

当你已经有一个能产生动作的多模态 actor 时，最自然的 critic 扩展通常不是另起一套编码器，而是：

- 在 actor 的共享前缀表征上接一个 value head

它的主要作用是：

1. 估计当前 prefix context 对应的未来回报
2. 作为 advantage 的基准
3. 给 online actor loss 提供样本加权依据

如果没有 value head，很多 hybrid RL 方案仍然能做，但会失去：

- 更稳定的 credit assignment
- 更自然的 online sample reweighting

## 15. hybrid RL 中 actor 实际优化的是什么

在这类实现里，actor 通常不是直接最大化 reward，而是优化一个经过 RL 重新加权的行为生成损失。

如果用非常直白的话说：

- 先看哪些 online 样本最终回报更高
- 再让模型更偏向拟合这些“更值钱”的动作 chunk

因此 online actor loss 的一般逻辑是：

1. 保留 flow matching 的生成式训练方式
2. 不直接丢掉原本的生成建模结构
3. 只是在样本权重上引入 RL 信号

这样做比“完全抛弃原生成目标、改成纯 policy gradient”更保守，也更适合从已训练 actor 出发继续微调。

## 16. 为什么总损失往往是三项相加

这类 hybrid RL 很常见的总损失结构是：

1. offline imitation loss
2. online actor loss
3. value loss

这三项分别回答三个问题：

1. offline imitation loss：
   - 不要忘记演示数据里已经学到的行为先验
2. online actor loss：
   - 让策略吸收环境反馈
3. value loss：
   - 让 critic 学会判断状态价值

如果只有 offline imitation loss：

- 就不是 RL 了

如果只有 online actor loss：

- 又容易把已学会的行为先验毁掉

如果没有 value loss：

- advantage 的质量通常会下降

## 17. 为什么很多工程实现里 RL 权重不会特别大

因为这类系统常常不是“从零训练 RL agent”，而是“在已有行为模型上做保守微调”。

因此常见策略是：

- 保留较强的 offline loss
- 给 online actor loss 一个中等权重
- 给 value loss 一个稳定存在的权重

这样做的逻辑是：

1. 保证行为不至于跑飞
2. 逐步吸收 online 信号
3. 减少真实部署前的分布崩溃风险

## 18. 上机、训练、评估是三件不同的事

### 18.1 训练

训练做的事是：

- 更新模型参数

### 18.2 上机

上机做的事是：

- 用现有模型在真实机器人上执行动作

### 18.3 评估

评估做的事是：

- 记录执行结果
- 统计成功率、稳定性、时长、动作平滑性等指标

所以“跑在机器人上”不等于“正在训练”。

大多数实际部署阶段都是：

- 只推理，不更新参数

## 19. 真实上机时，“用了 RL”到底是什么意思

这句话至少有两种完全不同的理解。

第一种理解：

- 上机时系统还在边执行边更新参数

第二种理解：

- 上机时使用的是一份经过 RL 微调后的 actor 权重

在大多数工程系统里，真实含义通常是第二种。

也就是说：

- RL 在训练阶段修改了 actor
- 上机阶段只是在使用被 RL 微调过的 actor

它不意味着：

- 机器人现场还在跑 policy gradient
- 机器人现场还在更新 value head

## 20. 为什么“之前训练了 10 个 epoch”不一定等于“训练了 RL”

如果那次训练跑的是纯离线训练入口，那么：

- 即使训练了很多 step 或很多 epoch
- 本质上仍然只是行为克隆或监督学习

是否“训练了 RL”，不看训练时长，而看训练闭环里有没有：

1. 环境交互
2. reward
3. replay buffer
4. critic/value
5. online data 参与优化

这也是一个非常重要的辨别规则。

## 21. 机器人 RL 项目里，最容易出问题的几个工程点

### 21.1 模型输入 schema 不一致

很常见的坑是：

- 数据集的观测键名和模型预期键名不一样

例如：

- 数据集里叫 top / wrist
- 模型里叫 camera1 / camera2

这类问题的本质不是模型坏了，而是：

- 缺一个 observation adapter 或 rename map

### 21.2 动作维度不一致

环境动作维度和模型内部最大动作维度经常不完全相同。

如果不处理，就会在：

- 前向投影
- flow matching score 计算
- 矩阵乘法

这些环节直接炸掉。

常见处理方式是：

- 补零到目标维度
- 或在必要时裁剪

### 21.3 依赖环境不完整

很多 RL 训练入口看起来能跑，但真正缺的是：

- 环境包
- 仿真依赖
- 视频解码依赖
- 离线 backbone 资产

因此工程上常常需要先做一件非常务实的事：

- 搭一个最小可跑通的代理环境，把链路打通

### 21.4 配置系统的布尔值解析

这是非常不起眼但很常见的坑。

有些配置系统只认：

- `true / false`

不认：

- `0 / 1`

所以 wrapper 脚本最好做一层布尔归一化。

### 21.5 离线和在线模式的资源管理

在网络不稳定或离线环境里，经常需要：

- 强制本地模型资产
- 禁用在线拉取
- 确认 tokenizer / backbone / preprocessor 都在本地可用

否则上机时可能不是模型本身出错，而是运行时在偷偷联网失败。

### 21.6 后台训练和监控方式

如果训练在某些托管执行环境里启动，普通 shell 后台进程可能会在会话结束时被清理。

因此训练监控要区分：

- 你自己机器上的终端后台
- 受限代理环境中的后台

## 22. 这套思路的能力边界

必须明确，这类“离线 VLA + hybrid RL”方案很强，但也不是万能的。

它能做的事情包括：

1. 在已有行为先验基础上做在线微调
2. 把 reward 信号通过 value 和 advantage 传回 actor
3. 在不彻底重写 actor 的前提下吸收 RL 信号

它不能自动解决的事情包括：

1. 真实任务 reward 是否合理
2. 仿真到真实机器人的 domain gap
3. 相机、时延、控制频率、机械误差等现实噪声
4. 如果离线基座很差，RL 是否还能救回来

所以它更像：

- 一个很强的“微调框架”

而不是：

- 一个不需要任务设计和实验验证的万能方案

## 23. 为什么说真实机器人上最重要的是“对比验证”

如果已经有：

- 一个离线基座 actor
- 一个 RL 微调后的 actor

那么最有价值的实验通常不是继续盲目加模块，而是做控制变量对比：

1. 同一套机器人
2. 同一套相机
3. 同一套任务文本
4. 同一套评估流程
5. 比较离线基座和 RL 微调版本

你真正想回答的问题是：

- RL 微调是否在真实执行里带来了更高成功率、更短时间、更平滑动作、更低失败率

## 24. 把这些知识做成 PPT，最合理的叙事顺序

如果下游 AI 要做 PPT，建议不要按“代码文件顺序”来讲，而按“问题驱动顺序”来讲。

一个推荐的讲法是：

### 第 1 页：问题定义

- 目标是什么
- 为什么要把 VLA、flow matching、RL 放到一起

### 第 2 页：系统总览

- 输入是什么
- 中间模块是什么
- 输出是什么

### 第 3 页：SmolVLA 架构

- 图像、语言、状态如何融合
- prefix context 是什么

### 第 4 页：动作生成方法

- 直接回归 vs ACT vs flow matching

### 第 5 页：为什么需要 RL

- 离线行为克隆的优点和局限
- 为什么要引入 online reward

### 第 6 页：hybrid RL 训练框架

- offline batch
- online rollout
- replay buffer
- value head

### 第 7 页：损失函数

- offline imitation loss
- online actor loss
- value loss
- 总损失

### 第 8 页：奖励与 bootstrapping

- reward 从哪来
- value target 怎么构造

### 第 9 页：shared prefix representation

- 为什么 actor 和 critic 共享前缀表征

### 第 10 页：RL 基础概念补课

- on-policy / off-policy
- PPO / DDPG / SAC
- V / Q
- 连续动作 / 离散动作

### 第 11 页：部署与上机

- 上机不是训练
- 推理时 RL 的真实含义

### 第 12 页：工程坑点与边界

- schema mismatch
- action dim mismatch
- dependency 问题
- reward 和现实任务不完全等价

### 第 13 页：实验结论应该怎么写

- 不要夸大
- 明确哪些结论已经验证，哪些还没有

## 25. 一组适合下游 AI 直接提炼成 PPT 标题的短句

下面这些短句是可以直接当 PPT 小标题或每页一句话总结用的。

- SmolVLA 的核心不是单一动作头，而是共享的多模态前缀表征。
- Flow matching 让连续动作 chunk 的生成更像一个逐步去噪过程，而不是一次性回归。
- Hybrid RL 的关键不是抛弃离线先验，而是在先验之上吸收在线环境反馈。
- Reward 定义的是目标，loss 定义的是学习方式，两者不能混为一谈。
- Chunk 级 collector 和 replay buffer 让 VLA 式动作生成能自然接入 off-policy 风格训练。
- Value head 的意义不是替代 actor，而是为 advantage 和 bootstrapping 提供稳定基准。
- 真实机器人上“用了 RL”通常意味着使用 RL 微调后的 actor，而不是现场在线更新参数。
- 离线训练、RL 微调、上机执行、评估统计是四个不同阶段，不能混着描述。
- 参数量不是能力的充分条件，总参数、可训练参数和激活参数必须分开看。
- 一套能跑的系统不等于一套已经完成真实任务验证的系统。

## 26. 最后的总判断

如果把这套知识浓缩成最终判断，可以这样说：

- SmolVLA 代表的是多模态前缀理解加 chunk 级动作生成。
- Flow matching 代表的是一种更适合连续动作生成的动作建模方式。
- Hybrid RL 代表的是在离线先验之上，用 online reward 和 value 继续调整 actor。
- shared prefix representation 是把 actor 和 critic 接到一起的关键接口。
- 真正难的从来不只是把代码接通，而是把 reward、训练流程、上机验证和结论边界都说清楚。

如果下游 AI 要做 PPT，最重要的不是把每个代码细节都画出来，而是把下面这条主线讲清楚：

- 一个多模态行为模型，如何从“看懂当前任务和状态”，走到“生成连续动作 chunk”，再走到“借助 RL 信号做保守微调”，最后真正用于机器人执行。
