# ACT (Action Chunking with Transformers)

ACT is a **lightweight and efficient policy for imitation learning**, especially well-suited for fine-grained manipulation tasks. It's the **first model we recommend when you're starting out** with LeRobot due to its fast training time, low computational requirements, and strong performance.

## Model Overview

Action Chunking with Transformers (ACT) was introduced in the paper [Learning Fine-Grained Bimanual Manipulation with Low-Cost Hardware](https://arxiv.org/abs/2304.13705) by Zhao et al. The policy was designed to enable precise, contact-rich manipulation tasks using affordable hardware and minimal demonstration data.

### Why ACT is Great for Beginners

ACT stands out as an excellent starting point for several reasons:

- **Fast Training**: Trains in a few hours on a single GPU
- **Lightweight**: Only ~80M parameters, making it efficient and easy to work with
- **Data Efficient**: Often achieves high success rates with just 50 demonstrations

### Architecture

ACT uses a transformer-based architecture with three main components:

1. **Vision Backbone**: ResNet-18 processes images from multiple camera viewpoints
2. **Transformer Encoder**: Synthesizes information from camera features, joint positions, and a learned latent variable
3. **Transformer Decoder**: Generates coherent action sequences using cross-attention

The policy takes as input:

- Multiple RGB images (e.g., from wrist cameras, front/top cameras)
- Current robot joint positions
- A latent style variable `z` (learned during training, set to zero during inference)

And outputs a chunk of `k` future action sequences.

## Installation Requirements

1. Install LeRobot by following our [Installation Guide](./installation).

## Training ACT

ACT works seamlessly with the standard LeRobot training pipeline. Here's a complete example for training ACT on your dataset:

```bash
lerobot-train \
  --dataset.repo_id=${HF_USER}/your_dataset \
  --policy.type=act \
  --output_dir=outputs/train/act_your_dataset \
  --job_name=act_your_dataset \
  --policy.device=cuda \
  --wandb.enable=true \
  --policy.repo_id=${HF_USER}/act_policy
```

### Training Tips

1. **Start with defaults**: ACT's default hyperparameters work well for most tasks
2. **Training duration**: Expect a few hours for 100k training steps on a single GPU
3. **Batch size**: Start with batch size 8 and adjust based on your GPU memory

### Distilling an Existing ACT Teacher

ACT now supports offline teacher-student distillation during the standard training loop. The student keeps the
usual behavior cloning loss and adds an auxiliary L1 loss against a frozen teacher action chunk.

```bash
lerobot-train \
  --dataset.repo_id=/path/to/your_dataset \
  --policy.type=act \
  --policy.kd=true \
  --policy.teacher_policy_path=/path/to/teacher/output_or_checkpoint \
  --policy.kd_weight=1.0 \
  --policy.kd_overlap_steps=50 \
  --policy.kd_temporal_decay=0.02 \
  --policy.chunk_size=50 \
  --policy.n_action_steps=50 \
  --output_dir=outputs/train/act_student
```

Notes:

- `teacher_policy_path` may point to a `pretrained_model` directory, a checkpoint directory, or an ACT output directory containing `checkpoints/last`.
- Distillation only supervises the overlapping action prefix between teacher and student, so you can safely train a shorter-horizon student from a longer-horizon teacher.
- Teacher and student must agree on observation keys, input shapes, and action dimensions.

Phase-1 support boundary:

- Only ACT-to-ACT distillation is supported.
- Teacher and student must share the same observation schema and action dimensionality.
- Phase 1 only supports reusing the student batch in the same normalized action space.
- The teacher snapshot is pinned during startup and written to run-level metadata at `output_dir/kd_teacher_metadata.json`.
- The run-level metadata uses the training metadata schema, including root keys such as `comparison_space`, `processor_compatibility`, and `metric_aggregation_mode`, plus nested teacher provenance under `teacher.original_path`, `teacher.pinned_pretrained_path`, `teacher.source_kind`, and `teacher.checkpoint_step`.

Phase-1 fail-fast behavior:

- Training resolves, loads, and attaches the ACT teacher bundle during startup instead of waiting for the first forward pass.
- Teacher and student preprocessors must pass the ACT processor compatibility check before the bundle is attached.
- Teacher and student must use the same rename behavior, normalization mapping, normalized observation keys, normalization stats, and image-key order.
- If any of those checks fail, training aborts before the first optimization step rather than silently comparing mismatched tensors.

Logging behavior:

- KD metrics are emitted through the normal training tracker, including `kd_l1_loss`, `kd_weighted_l1_loss`, `kd_overlap_steps`, and the model-side `kd_to_bc_ratio`.
- In ACT, `kd_to_bc_ratio` refers to the weighted KD loss divided by the BC loss. If an older output dict lacks that model-side ratio, the trainer backfills `kd_weighted_to_bc_ratio` instead of reusing the `kd_to_bc_ratio` name.
- Under multi-process training, KD metrics are reduced across ranks before they are logged, so the tracker and WandB see global values instead of rank-0-only values.

Explicit non-goals for phase 1:

- No cross-policy distillation.
- No hidden-state or latent distillation.
- No automatic canonicalization path for teacher/student processors that do not already match.

## Evaluating ACT

Once training is complete, you can evaluate your ACT policy using the `lerobot-record` command with your trained policy. This will run inference and record evaluation episodes:

```bash
lerobot-record \
  --robot.type=so100_follower \
  --robot.port=/dev/ttyACM0 \
  --robot.id=my_robot \
  --robot.cameras="{ front: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}}" \
  --display_data=true \
  --dataset.repo_id=${HF_USER}/eval_act_your_dataset \
  --dataset.num_episodes=10 \
  --dataset.single_task="Your task description" \
  --policy.path=${HF_USER}/act_policy
```
